# 前端验证工作指南

## 1. 创建演示学生（必需前置步骤）

后端需要真实的演示学生数据才能验证前端。没有这一步，前端看到的要么是空的，要么是写死的假数据。

### 1.1 环境要求

- conda 环境已配好
- MySQL 服务已启动
- LLM API Key 已配置（DashScope 或兼容接口）
- 图数据库（KnowLion / RAG 服务）已启动，需要时设环境变量开启

### 1.2 播种命令

在项目根目录下，激活 conda 环境后执行。**这三个环境变量缺一不可**——它们分别控制"允许调真实 LLM""允许调真实知识库""允许写数据库"。

```bash
conda activate lianjue

# 播种全部 3 个学生（进度低/中/高），预计 5-10 分钟
RUN_LLM_TESTS=1 RUN_REAL_RAG_TESTS=1 RUN_DB_TESTS=1 python -m pytest tests/total_agent/test_seed_demo_students.py -v

# 只播中等进度学生（调试用，3-5 分钟）
RUN_LLM_TESTS=1 RUN_REAL_RAG_TESTS=1 RUN_DB_TESTS=1 python -m pytest tests/total_agent/test_seed_demo_students.py -v -k demo_medium
```

### 1.3 播种会产出什么

播种脚本会走完整的生产流程：创建用户 → 模拟学习记录 → 生成画像 → 运行推荐 → 确认学习计划 → 构建知识树 → 生成学习资料。

| 产物 | 存放位置 | 说明 |
|------|------|------|
| 用户记录 | 数据库 users 表 | 用户名格式 `demo_{低/中/高}_{随机码}`，统一密码 `demo123` |
| 学习画像 | 磁盘 `profiles/` 目录 | 包含知识掌握度、学习风格、周进度等 |
| 学习计划 | 数据库 plan 相关表 | 推荐路径确认后生成的步骤列表 |
| 知识树 | 数据库 + 磁盘 `study_graph/` | 学生已掌握的、学习中、薄弱的知识节点 |
| 生成资源 | 磁盘 `generative/` 目录 | LLM 生成的学习文档或思维导图 |
| 运行摘要 | `tests/artifacts/total_agent/demo_students/summary.json` | 记录每次播种的用户名、ID、密码，方便查找 |

### 1.4 多次播种注意

- 每次播种都会创建**新用户**，不会覆盖旧的
- 旧用户可以手动清理：`DELETE FROM users WHERE user_name LIKE 'demo_%';`
- 播种后调 `GET /api/demo_students` 能拿到最新 3 个学生
- 如果重复播种多次，数据库里会积压大量 demo 用户，建议定期清理

### 1.5 启动服务

```bash
# 后端
cd Lianjue_Backend
conda activate lianjue
python app.py

# 前端
cd Lianjue_Frontend
npm run dev
```

**最重要的环境变量：** 前端 `.env` 文件里的 `VITE_USE_MOCK_API`：
- 设 `true` → 全站用写死的假数据（`src/data/e2eFixtures.ts`），不调后端
- 设 `false` → 走真实 API，这才是验证的目标

## 2. 如何判断看到的数据是真的还是假的

### 2.1 核心开关

前端代码里所有数据加载都经过同一个判断：读取 `VITE_USE_MOCK_API`，如果为 `true` 就用本地写死的数据，如果为 `false` 就调后端接口。

验证前端之前，**第一件事就是确认这个开关是 `false`**。

### 2.2 一眼分辨假数据和真数据

| 看哪里 | 假数据特征 | 真数据特征 |
|--------|-----------|-----------|
| 登录页 | 3 个用户叫 demo_low / demo_medium / demo_high，ID 是 145/142/152 | 用户名带随机码，每次播种不同 |
| 学习画像 | 所有数值和标签都一模一样 | 不同用户数值不同，低/中/高有明显区分 |
| 学习计划 | 永远是固定的 6 步，标题是短中文词 | 步骤数和标题每次播种都可能变化 |
| 知识树 | 节点是固定的，不会变 | 节点数因播种而异 |
| 推荐路径 | 永远是同一条路径 | 不同用户路径不同，受profile影响 |
| 底部的图谱 | 用户 ID 显示 145 | 显示真实的动态 ID |

### 2.3 最快确认方法

打开浏览器开发者工具（F12）→ Network（网络）面板。登录后看有没有发 API 请求：

- 如果**完全没有网络请求** → 开关是 `true`，改 `false` 重启前端
- 如果有请求但**返回 404** → 后端缺路由，代码版本不对
- 如果有请求且返回 `{"success": true}` 但数据为空 → 该用户对应的数据没生成，seed 可能失败了

## 3. 各模块验证要点

### 3.1 登录页

**路径：** `/login`

**期望看到：** 3 张学生卡片，分别标注低/中/高进度。每张卡片有 emoji 头像、一句话描述、学习周进度条、几个标签。点击卡片直接登录，也可以用用户名 + 密码 `demo123` 手动登录。

**出问题时排查方向：**
- 没卡片 → 调 `GET /api/demo_students` 看看后端有没有返回学生列表
- 卡片信息不对劲 → 说明 seed 没跑通，去数据库查 users 表有没有 `demo_%` 用户
- 登不上去 → 密码是 `demo123`，确认后端 login 接口正常

---

### 3.2 左侧栏 — 学习计划

**路径：** 主界面左侧边栏，翻页按钮切到 "Plan"

**期望看到：** 一个步骤列表，"步骤 1: xxx""步骤 2: xxx"这样排列。当前正在学的步骤会高亮显示（蓝色标题 + 播放图标），已完成的打绿色对勾，还没开始的显示灰色空心圆。点击任意步骤可以展开看详细的学习目标，再点一下收起。默认只展开当前步骤。底部有一条进度条显示完成百分比。

**验证重点：**
- [ ] 步骤标题是简短可读的课程名（比如"大数据存储与管理"），不是完整长句子
- [ ] 展开后的学习目标是短词短语，不是"将带领学生了解…"这种句子碎片
- [ ] **三个不同进度的学生，学习计划应该不一样**——进度高的应该跳过基础章节，进度低的从第一章开始
- [ ] 如果三个人的计划完全一样 → 说明画像数据没起作用，推荐算法没识别出"这个学生已经会了"

**出问题时排查方向：**
- 显示"暂无学习计划" → 该用户的推荐步骤没跑通，seed 里推荐阶段挂了
- 步骤标题巨长 → 后端给的 title 是 syllabus 原文而不是课程主题名
- 学习目标乱七八糟 → syllabus 解析时把正文碎片当成知识点标签了

---

### 3.3 底部栏 — 学习图谱预览

**路径：** 主界面底部，点"学习图谱预览"展开

**期望看到：** 左边是推荐路径的节点关系图，当前推荐路径用紫色高亮，无关节点半透明。上方有候选路线按钮（编号 1、2、3），点不同编号切换不同的推荐路线。"确认路径"按钮点完变绿，同时左侧栏的学习计划会刷新成刚确认的计划。右边是知识树图，节点大小代表掌握程度。

**验证重点：**
- [ ] 推荐路径的节点数量合理——不应该把课程 16 周全排上去，应该只推荐学生还没掌握的
- [ ] 点"确认路径"后，左侧栏的学习计划要刷新（不是停留在旧数据）
- [ ] 如果确认后计划不刷新 → 是前端状态管理的问题

**出问题时排查方向：**
- 没有推荐路径 → seed 的推荐阶段失败了，或者该用户没有存推荐快照
- 推荐路径等于全部课程章节 → 推荐算法没利用画像数据做过滤
- 确认按钮一直转圈 → 后端 accept 接口挂了

---

### 3.4 左侧栏 — 学习画像摘要

**路径：** 左侧边栏翻页到 "Profile"

**期望看到：** 学习目标描述、学习风格偏好、综合掌握度百分比、实操能力、辍学风险等级。还有薄弱知识点标签（红色小方块）。

**验证重点：**
- [ ] **三个学生数值有明显差别**——高手应该综合掌握度高、辍学风险低，新手相反
- [ ] 如果三个人全都是 26% → 画像没拉开差距

---

### 3.5 左侧栏 — 知识树

**路径：** 左侧边栏翻页到 "Knowledge Tree"

**期望看到：** 顶部统计"已掌握 X / 学习中 Y / 薄弱 Z"（绿色/蓝色/橙色圆点区分）。下面列出前几条知识点，每条有圆点颜色、标题、掌握度百分比。

**验证重点：**
- [ ] 进度低的学生：大量"薄弱"，少量"学习中"，几乎没"已掌握"
- [ ] 进度中等的学生：三类混合分布
- [ ] 进度高的学生：较多"已掌握"和少量"薄弱"
- [ ] 如果三个人全是"薄弱" → 知识树数据没按预期生成

---

### 3.6 右侧栏 — 学习指标面板

**路径：** 主界面右侧边栏，6 个子页面用左右箭头翻页

| 子页面 | 内容 | 怎么算对 |
|--------|------|---------|
| 总览 | 综合指标卡片 | 数据来自真实画像，不同用户数值不同 |
| 活跃 | 学习活动甘特图 | 有实际的活动时间段，不是空图 |
| 画像雷达 | 8 维能力雷达图 | 不同进度的用户图形状明显不同，不是正八边形 |
| 学习日历 | 周进度时间线 | 每周有进度标记，不是全为 0 |
| 学习文件 | 生成的资源列表 | 中等进度有文档，高进度有思维导图 |
| 知识库 | 知识库搜索 | 输入关键词能返回相关结果 |

## 4. 常见问题速查

### 4.1 三个学生的计划完全一样

所有学生都从"第一章"起步，没跳过任何已掌握内容。

**原因：** 推荐系统没拿到有效的画像匹配——它不知道"这个学生已经会 HDFS 了"。数据流是这样的：学习记录被汇总成知识点标签（"HDFS 基础 掌握度 0.9"），但课程章节的名字是 syllabus 原文（"分布式文件系统及主流技术 HDFS"），两个名字对不上，系统误判"这个学生什么都不会"，于是从头推荐。

**怎么修：** 已加了三层优化：先做字符串精确匹配、再做子串匹配（"HDFS"包含在长标题里）、最后用 LLM 做语义匹配。重播 seed 再看效果。

### 4.2 画像数值没区分度

三个学生的综合掌握度非常接近（比如都是 20% 多），分不出高低。

**原因：** 画像有两套评分体系。一套是"知识点维度"（按知识点标签打分，能区分），另一套是"周维度"（按每周课程打分，目前都是 0）。推荐主要看周维度，所以觉得大家都没学过。

**怎么修：** 知识点标签 → 课程章节的 LLM 语义对齐（同 4.1 的修复），这样即使周维度全是 0，推荐也能从知识点维度判断。

### 4.3 步骤标题过长

标题显示的是完整句子，不是课程名。

**怎么修：** 已修复。现在 syllabus 解析时优先提取课程主题名（冒号前面的部分），比如"大数据存储与管理：分布式数据库…"会被提取成"大数据存储与管理"。

### 4.4 确认路径后计划没刷新

点了底部图谱的"确认路径"按钮变绿了，但左侧学生的学习计划还是旧的那份。

**怎么修：** 已修复。确认成功后会自动触发计划重取。

## 5. 有用命令速查

```bash
# 查最新 demo 学生
curl http://localhost:5000/api/demo_students

# 查某用户的 plan（替换 <uid>）
curl "http://localhost:5000/api/learning_plan?user_id=<uid>&syllabus_id=29"

# 查某用户的 profile
curl -X POST http://localhost:5000/api/learning_profile_detail \
  -H "Content-Type: application/json" \
  -d '{"user_id": <uid>, "syllabus_id": 29}'

# 查出某用户的推荐快照列表
curl "http://localhost:5000/api/recommendations?user_id=<uid>&syllabus_id=29&limit=3"

# 跑后端默认回归（不含 LLM/RAG/DB，只测逻辑）
python -m pytest tests/ -q --ignore=tests/total_agent

# 重播指定 level
RUN_LLM_TESTS=1 RUN_REAL_RAG_TESTS=1 RUN_DB_TESTS=1 python -m pytest tests/total_agent/test_seed_demo_students.py -v -k demo_high
```
